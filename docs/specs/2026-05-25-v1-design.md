# wiki-manage v1.0 设计文档

**版本**：v1.0 (draft)
**日期**：2026-05-25
**状态**：待 user review
**取代**：wiki-manage v0.1.x（skill 形态，归档在 `~/AI/wiki-manage-legacy`）

---

## 1. 背景与定位

### 1.1 为啥推翻 v0.1.x

v0.1.x 是 skill 形态的跨平台插件，问题：
- skill = 给 AI 看的 prompt 说明书，**无 enforcement**（AI 会忘 / 写错 / 偷懒）
- 三平台分发机制各异（Claude marketplace / Codex toml / Cursor symlink），维护成本高
- 没有团队级"治理"能力（统计 / 健康度 / 知识图谱 / 标记 / 升级流程）
- "知识库混乱、链路不通、无效信息、误操作"这些 pain 都没解决

### 1.2 v1.0 是什么

不是 v0.1.x 的迭代——是**完全重写**。形态从「skill 插件」变成「**本机服务 + Web 治理面板 + MCP**」。

| 维度 | v0.1.x | v1.0 |
|---|---|---|
| 形态 | skill 插件 | 本机服务进程 |
| AI 接入 | 三平台各装 plugin | MCP 协议，三平台 10 行配置统一 |
| 知识协议 | 扁平 `me/projects/concepts/sources` | Karpathy `domains/global/staging/routes` |
| Enforcement | 无（AI 自律） | git pre-commit hook + Web UI 治理 |
| 团队视图 | 无 | Web 仪表板（统计 / 图表 / 标记 / 知识图谱） |
| 双仓 | 不支持 | 个人本地 + 团队 git，物理分离 |
| 任务记录 | 无 | 标记 + AI 整理闭环 |
| LLM 集成 | 无 | Web 后端调 LLM 整理（每日定时 + 手动触发） |

### 1.3 目标用户

**只服务开发者**（你明确决策）。不考虑：
- ❌ 领导可见（不做静态导出 / 不部署内网域名）
- ❌ 非技术用户（不做账号 / 权限 / RBAC）
- ❌ 多人协作平台（依赖 git 处理协作）

## 2. 核心思想

### 2.1 「人标记 + AI 整理」工作流

```
Web 服务（治理）              AI 工具（执行）
─────────────              ─────────────
用户在 Web 点标记       ──┐
- 升级到团队仓                │
- 待完善                      │
- 待重写                      ↓
- 待删除等              生成「待处理清单」（作为 markdown frontmatter 状态）
                              ↓
                        AI 工具通过 MCP 读清单
                              ↓
                        AI 按标记类型整理 markdown
                              ↓
                        AI 调 wiki.commit_draft 落地
                              ↓
                        清空标记 + 写 processing log
                              ↓
                        用户在 Web 上看到 "AI 完成 N 条"
                              ↓
                        错了 → 再标记 / git revert
```

**关键分工**：人擅长判断，AI 擅长执行。

### 2.2 双仓物理隔离

```
~/wiki-team/                                ~/wiki-self/
git clone 自团队远端 repo                    本地，不推任何远端
                                            
团队 wiki / 共识 / 架构                       个人偏好 / 任务记录 / 草稿
经过验证、对全员有价值                          原始踩坑、个人决策
通过 git PR 进入                              直接写
```

**升级**（个人→团队）：显式操作，通过 AI 工具调 MCP API 完成。**降级或同步**没有（个人仓不暴露给团队仓）。

### 2.3 跨 AI 工具走 MCP

放弃 v0.1.x 的「三平台各装 plugin」模式。改为：

```
本机服务 (localhost:7081) 同时提供：
├── HTTP /                  Vue SPA（浏览器访问）
├── HTTP /api/*             REST API（前端调）
└── HTTP /mcp + /mcp/sse    MCP HTTP/SSE endpoint（AI 工具调）

三平台配置 100% 一致：
{
  "mcpServers": {
    "wiki": { "url": "http://localhost:7081/mcp" }
  }
}
```

跨平台兼容**消失为非问题**——MCP 是协议层统一的。

## 3. 系统架构

### 3.1 全景

```
┌──────────────────────────────────────────────────────────────────┐
│  开发者本机                                                       │
│                                                                   │
│  ┌──────────────────────┐         ┌──────────────────────┐       │
│  │ Claude Code/Codex/   │         │ 浏览器                │       │
│  │ Cursor (秘书 AI)     │         │ (治理面板)            │       │
│  └─────┬────────────────┘         └─────────┬────────────┘       │
│        │ MCP HTTP/SSE                       │ HTTP                │
│        │  POST /mcp                         │ GET /               │
│        │                                    │ GET/POST /api/*     │
│        └─────────────┬──────────────────────┘                     │
│                      ↓                                            │
│   ┌─────────────────────────────────────────────────────────┐    │
│   │  本机服务进程（localhost:7081）                          │    │
│   │  单进程 Node.js (Fastify / NestJS)                       │    │
│   │                                                          │    │
│   │  内存索引：                                               │    │
│   │  - frontmatter 索引（按 domain/type/status）             │    │
│   │  - 全文索引 (Lunr / FlexSearch)                          │    │
│   │  - 关系图（wikilink + cross_refs）                       │    │
│   │  - 路由表（_routes.md 解析）                              │    │
│   │  - 待处理清单（marked_for 字段聚合）                      │    │
│   │                                                          │    │
│   │  执行逻辑：                                                │    │
│   │  - markdown 读写                                          │    │
│   │  - schema 校验                                            │    │
│   │  - LLM API 调用（用户配自己的 token）                     │    │
│   │  - 定时任务（每日整理 + cron）                             │    │
│   │  - git 操作（add/commit/push）                            │    │
│   └─────┬──────────────────────────────────────────┬────────┘    │
│         │                                          │              │
│         ↓                                          ↓              │
│  ┌──────────────────────┐         ┌──────────────────────┐       │
│  │ ~/wiki-team/         │         │ ~/wiki-self/         │       │
│  │ (git clone)          │         │ (本地 only)           │       │
│  │ Karpathy 协议         │         │ Karpathy 协议         │       │
│  │ .md 文件 SoT          │         │ .md 文件 SoT          │       │
│  │ .git/hooks/pre-commit│         │ .git/hooks/pre-commit│       │
│  └──────┬───────────────┘         └──────────────────────┘       │
│         │ git push                                                │
└─────────┼─────────────────────────────────────────────────────────┘
          ↓
┌──────────────────────────────────────────────────────────────────┐
│  GitHub Enterprise / GitLab                                       │
│  wiki-team.git                                                    │
│  + GitHub Action: lint workflow（push 时跑同套校验）              │
└──────────────────────────────────────────────────────────────────┘
```

### 3.2 关键设计点

- **单进程**：HTTP + MCP 共用 Fastify 进程，**不是微服务**
- **零数据库**：所有状态在 markdown frontmatter 或内存。崩了从 markdown 重建。
- **零长期持久化**：除了 git 仓库本身（git 是文件系统的，不是数据库）
- **个人仓不上服务器**：物理隔离，隐私边界靠操作系统
- **团队同步走 git**：不重做协作 / 冲突 / merge 工具

## 4. 数据模型

### 4.1 仓库结构（团队 + 个人共享同一套，沿用 Karpathy）

```
~/wiki-team/  或  ~/wiki-self/
├── AGENTS.md                       # 本仓协议
├── _routes.md                      # 关键词路由表
├── overview.md                     # 顶层地图
├── log.md                          # 活动日志
│
├── raw/sources/                    # 原件（只读）
├── raw/assets/                     # 图片等
│
├── wiki/
│   ├── domains/<slug>/
│   │   ├── overview.md
│   │   ├── sources/<name>.md
│   │   ├── concepts/<name>.md
│   │   ├── queries/<name>.md
│   │   ├── entities/<name>.md
│   │   ├── modules/<id>-<slug>/    # 业务模块（6 文件）
│   │   └── gotchas/                # 踩坑库
│   ├── global/concepts/
│   ├── global/entities/
│   ├── staging/
│   └── templates/
│
├── task-log/                       # 任务记录（个人仓主力）
│   └── YYYY/MM/YYYY-MM-DD-<slug>.md
│
├── archive/<分类>-<YYYY-MM-DD>/    # 归档（不 rm）
└── revisions/                       # 审计 artifact
```

### 4.2 元数据分层（核心 vs 维护）

每个 .md 的 frontmatter **分两节**：

```yaml
---
# === 知识本体（AI 查询 / 整理 / 路由时都看）===
tags: [concept]
domain: flux-tms
type: concept
status: active | archived | needs-improvement | low-value | draft
priority: high | medium | low      # AI 排序用
confidence: high | medium | low    # 实验性 vs 已验证
date_created: 2026-05-25
date_updated: 2026-05-25
triggers: [db-query, oracle-bug]   # 关键词路由命中用

# === 维护信息（人看为主；AI 整理时才看；AI 查询时忽略）===
_meta:
  comments: []                     # 评论数组（短的 inline，长的引用外部文件）
  marked_for: null                 # null | upgrade-to-team | rewrite | delete | split | merge | needs-detail
  marked_by: null                  # git author
  marked_at: null                  # ISO 时间戳
  marked_note: null                # 标记附言（短描述为啥标）
  review_due: null                 # YYYY-MM-DD 自动提醒
  owners: []                       # 谁负责（git author 自动）
---

# concept 正文 markdown ...
```

### 4.3 AI 三种行为下看哪些

| AI 行为 | 看 frontmatter 主区 | 看 `_meta` | 看正文 |
|---|---|---|---|
| 查询知识（用户问问题） | ✅ | ❌ | ✅ |
| 整理标记（处理 marked_for） | ✅ | ✅ | ✅ |
| 路由匹配 | ✅（triggers） | ❌ | ❌ |

→ 在 ~/.claude/CLAUDE.md 等 global rules 里约束 AI："查询时忽略 `_meta`"

### 4.4 标记系统（完整清单）

| `marked_for` | 适用仓 | 含义 | AI 处理 |
|---|---|---|---|
| `upgrade-to-team` | 个人仓 | 这条值得同步到团队 | 抽精华写到团队仓对应位置 + 留链接回原 |
| `rewrite` | 两仓 | 内容有问题，重写 | 改 markdown，保留原意 |
| `delete` | 两仓 | 删除 | mv 到 archive/（不真删） |
| `split` | 两仓 | 太长，拆分 | 拆成多个文件 + 更新 routes |
| `merge` | 两仓 | 跟另几条该合并 | 合并 + 归档原文件 |
| `needs-detail` | 个人仓 | 缺细节请补充 | AI 补内容（或提示用户补） |
| `archive-expired` | 两仓 | 过期清理 | 移到 archive/ |

### 4.5 命名规则（server 校验）

- 文件名：**小写 kebab-case**
- domain slug：白名单（由 `_routes.md` 隐式定义）
- module slug：`<module-id>-<英文名>`，如 `t0119-appointment`
- task-log 文件名：`YYYY-MM-DD-<slug>.md`

## 5. MCP API 设计

### 5.1 工具清单（v1 暴露 ~10 个）

| 工具 | 类型 | 用途 |
|---|---|---|
| `wiki.search` | 查询 | 跨仓全文搜索 |
| `wiki.get` | 查询 | 取单页全文 |
| `wiki.get_module` | 查询 | 取模块 6 文件全套 |
| `wiki.routes_match` | 查询 | 关键词路由匹配 |
| `wiki.list_domains` | 查询 | 列活跃 domains |
| `wiki.list_pending` | 查询 | 列待处理标记清单 |
| `wiki.prepare_draft` | 写入（两段式之一） | 准备草稿不落地 |
| `wiki.commit_draft` | 写入（两段式之二） | 用户确认后落地 |
| `wiki.append_to` | 写入 | 受控追加（task-history 等） |
| `wiki.mark` | 写入 | 设置 `_meta.marked_for` 字段 |
| `wiki.clear_mark` | 写入 | AI 处理完后清空标记 + 写 processing log |
| `wiki.lint` | 运维 | 跑校验返报告 |

### 5.2 关键工具：`wiki.list_pending`

```typescript
input: {
  scope?: 'team' | 'self' | 'all'
  marked_for?: 'upgrade-to-team' | 'rewrite' | 'delete' | ...
  limit?: number   // 默认 20
}

output: {
  items: Array<{
    path: string
    title: string
    marked_for: string
    marked_by: string
    marked_at: string
    marked_note: string
    domain: string
    excerpt: string  // 前 200 字
  }>
}
```

AI 在 skill 指引下定期调这个工具，按 marked_for 类型处理。

### 5.3 写入两段式（避免 AI 写半成品）

```
1. AI 调 wiki.prepare_draft({ type, fields }) → 返回 draft_id + 草稿全文
2. AI 把草稿全文给用户预览
3. 用户确认 → AI 调 wiki.commit_draft(draft_id) → 真正写入 + 追加 log
```

服务端校验：schema 完整、路径合法、不冲突、domain slug 白名单。

## 6. Web 治理面板

### 6.1 页面清单

| 页面 | 内容 |
|---|---|
| 首页 / 仪表板 | 总知识数、按 domain 分布、按 status 分布、增长曲线、待处理标记数 |
| 浏览（团队仓） | 左侧 domain 树 / 中间内容 / 右侧 metadata |
| 浏览（个人仓） | 同上 |
| 搜索 | 全文 + 过滤（domain/type/status/priority） |
| 知识图谱 | 力导向图（wikilink + cross_refs） |
| 待处理 | 所有 `marked_for != null` 的清单 + 标记历史 |
| Activity | 最近 git commit + 任务记录 + AI processing log |

### 6.2 关键交互：标记

每个页面右上角下拉菜单：
- 升级到团队仓
- 标记待重写
- 标记待删除
- 标记待拆分
- 标记低价值（status → low-value）
- 设置 review_due
- 加评论
- 修改 priority / confidence

点击 → 后端写 `_meta` → git commit（author = 当前用户）

### 6.3 LLM 触发器

页面顶部右上角有「让 AI 处理待处理 (N)」按钮 →
- 调本机服务的 LLM endpoint
- LLM 读 `wiki.list_pending`
- 按标记类型处理
- 写 processing log
- 完成后通知用户

**自动定时**：每日 03:00（用户可配）自动跑一遍。

## 7. Enforcement 三层

| 层 | 位置 | 何时介入 | 拦什么 |
|---|---|---|---|
| L1 | MCP API（服务端） | AI 调 wiki.* 时 | schema、命名、路径、domain slug |
| L2 | git pre-commit hook | `git commit` 时 | 同 L1（同一套 lint） |
| L3 | GitHub Action CI（团队仓） | push 到远端时 | 同 L1（最后兜底） |

人手动改 .md 服务端不监听，但下次 AI 查询时检查 mtime 自动重读。

## 8. 三阶段交付

### 阶段 1：基础设施 + AI 端（1-2 周）

**产出**：
- `lint/` 目录：schema 定义（JSON Schema）+ lint 规则集
- `bin/pre-commit-hook.sh`：git hook 脚本
- `bin/wiki-init.sh`：仓初始化脚本
- `templates/`：从 wiki-manage-legacy 复用 7 个模板（concept / source / project-readme 等）
- `~/.claude/CLAUDE.md` 等三平台 global rules 模板

**用户立刻能用**：AI 不再瞎写，git 拦错。现有 `~/AI/wiki` 跑起来。

### 阶段 2：本机 Web 服务（4-6 周）

**产出**：
- `server/`：Fastify + 内存索引 + REST API + MCP HTTP/SSE
- `web/`：Vue 3 + Element Plus + ECharts SPA
- `Dockerfile`：一键启动
- LLM API 集成（Claude / OpenAI / 国产可选）
- 定时任务（cron）

**用户立刻能用**：治理面板成型，能在浏览器看 / 标记 / 统计。

### 阶段 3：AI 工具升级（1 周）

**产出**：
- 升级 skill / global rules：让 AI 知道有 MCP，调 `wiki.list_pending` 消费待处理清单
- AI 整理工作流（按 marked_for 类型）

**用户立刻能用**：标记 + AI 整理闭环完成。

## 10. 全局规则（marker 包裹）

由 `wiki-init.sh` 写入 `~/.claude/CLAUDE.md` 等：

```markdown
<!-- wiki-manage:start v1.0 -->
## 知识库（wiki-manage v1.0 托管）

本机服务在 localhost:7081，AI 通过 MCP wiki.* 工具访问。

**入场加载**：
- 调 `wiki.list_domains()` 看活跃 domain
- 用户消息含关键词时调 `wiki.routes_match(text)` 加载相关页

**主动行为**：
- 用户表达偏好 / 工作流 → `wiki.prepare_draft(scope='self')`
- 用户分享外部资料 → 原件 cp 进 raw/sources/，摘要走 prepare_draft
- 任务收尾 → 询问用户「要记录吗」，得到明确授权后才 wiki.append_to task-log

**消费待处理清单**：
- 用户说「处理一下 wiki 待办」 → 调 `wiki.list_pending` 拿清单
- 按每条的 `marked_for` 类型处理（升级 / 重写 / 删除 / 拆分等）
- 处理完 `wiki.clear_mark` 清标记

**纪律**：
- 查询时忽略 `_meta` 节
- 任务记录前必须用户明确授权
- 删除 = 归档，绝不 rm
<!-- wiki-manage:end -->
```

marker 包裹保证可升级 / 可卸载（v0.1.x 已验证过这套）。

## 11. 实现技术栈

| 层 | 技术 | 理由 |
|---|---|---|
| 后端 | **Node.js + Fastify** | 单文件起进程、轻量、MCP SDK 官方 Node 实现成熟 |
| MCP SDK | `@modelcontextprotocol/sdk` | 官方主推 |
| 全文索引 | **FlexSearch** | 比 Lunr 快、中文友好 |
| 中文分词 | nodejieba | 中文全文搜索精度 |
| 前端 | **Vue 3 + Vite + TypeScript + Element Plus** | 你团队栈、默认好看 |
| 图表 | **ECharts** | 国内成熟 |
| 关系图 | **mermaid (静态) + d3 force-graph (交互)** | 双层方案 |
| Git 操作 | `simple-git` | Node 库 |
| Markdown | `remark` + `gray-matter` | 解析 + frontmatter |
| LLM 集成 | `@anthropic-ai/sdk` / `openai` / 兼容 | 用户配自己的 token |
| 部署 | **Docker** | docker run 一行起 |
| 配置 | `~/.wiki-manage-config.json` | 跨 AI 工具共享 dotfile |
