## 1. 工具定位

### 是什么

让 AI 工具（Claude Code / Codex / Cursor）按规范**维护**个人 wiki 知识库的工具。

```
[ AI 端 ] SKILL/插件（工作流文档）  ──→  按规范操作 wiki
[ 用户端 ] 本机 Web 服务            ──→  浏览 / 标记知识状态
[ 数据 ]  ~/AI/wiki/（markdown SoT）
```

### 不是什么

- ❌ 不是 wiki 编辑器（Obsidian 已经做得很好）
- ❌ 不是团队协作平台（v1.0 砍掉团队仓，只服务个人）
- ❌ 不是 RAG 向量库（处理结构化精炼知识，不是非结构化大文档）
- ❌ 不是中心化部署服务（每个开发者本机一份）
- ❌ 不要 enforcement 兜底层（无 git hook / 无服务端写入校验）

### 核心价值

**AI 按规范维护知识库**——这是 v0.1.x 没做好的事，是 v1.0 唯一聚焦点。

---

## 2. 三大组件分工

### 组件 A：SKILL/插件（AI 端核心）

含**工作流文档**，告诉 AI：
- 如何读 wiki（grep + Read file tools）
- 如何写 wiki（路径推断 / frontmatter / 命名规范 / 关系维护）
- 如何**消费用户在 Web 上的标记**（拿到待办清单 → 按标记类型走对应工作流）

**这是工具的核心，决定 AI 行为是否规范**。

### 组件 B：本机 Web 服务

**唯一职责**：服务用户。

- 浏览 wiki（极简文件树）
- 用户标记（v1.0 只支持「有疑问」一种）
- 提供 `GET /api/marked` 给 AI 查待办清单

**不做**：写入校验、规范化、LLM 集成。Web 服务**不参与 AI 工作流**。

### 组件 C：wiki 仓

`~/AI/wiki/`（路径可配置，默认沿用现有）

- Karpathy LLM Wiki 协议（domains / global / staging / routes / revisions）
- markdown 为唯一 SoT
- 由 AI 直接 file tools 读写

## 3. 工作模式

### 3.1 AI 操作 wiki = 自律走 SKILL 工作流

```
用户："这次踩坑记一下"
   ↓
AI 读 SKILL 工作流：
  1. grep 找相似已有内容
  2. 推断 type / domain / 路径
  3. 写 frontmatter
  4. Write 文件
  5. 追加 log.md
   ↓
AI 用 Read/Grep/Write file tools 直接操作 ~/AI/wiki/
```

**无 enforcement 层**——不做 git hook、不做服务端校验。AI 写错就是错，靠用户在 Web 上「标记有疑问」之后让 AI 整理。

### 3.2 用户标记驱动 → AI 整理

```
用户在 Web 上看到某条 wiki 内容有问题 → 点「标记有疑问」
   ↓
Web 服务写 .md 的 frontmatter：_meta.marked_for: question
   ↓
（异步）用户跟 AI 说「处理一下 wiki 待办」
   ↓
AI 调 GET localhost:7081/api/marked 拿清单
   ↓
AI 按 SKILL 中的「处理标记」工作流，对每条 marked_for=question 的：
   - 读内容
   - 判断问题（含糊？过时？错误？）
   - 重写 / 拆分 / 标记删除（视情况）
   - 清空 marked_for 字段
   ↓
完成
```

**单一路径**：AI 自律 + 用户标记驱动。无并行防御机制。

## 4. MVP 范围（v1.0）

**只做一个端到端闭环**：「**标记有疑问 → AI 整理**」

**v1.0 IN**：
- SKILL 工作流（含「读」「写」「处理 question 标记」三个）
- 三平台分发（Claude / Codex plugin + Cursor snippet）
- Web 服务最小版：
  - 文件树浏览
  - 点击查看内容
  - 「标记有疑问」按钮
  - `GET /api/marked` endpoint
- wiki-init 脚本（初始化 ~/AI/wiki/ + 注入 global rules marker）

**v1.0 OUT（v1.1+ 再加）**：
- 其他标记类型（重写 / 删除 / 拆分 / 合并 / 待完善）
- 仪表板 / 统计 / 图表
- 全文搜索
- 知识图谱可视化
- 评论 / 优先级 / 置信度等元数据
- LLM API 集成（异步整理任务）
- 任务记录子系统
- git hook 校验（用户已明确反对）

## 5. 三平台分发

| 平台 | 分发载体 | 用户安装步骤 |
|---|---|---|
| Claude Code | Plugin marketplace | gh marketplace install |
| Codex | Plugin marketplace | 同上 |
| Cursor | User Rules（无 plugin 系统） | 手动粘贴 snippet |

**开发维护一份 SKILL.md**，三平台分发载体各自包装这份内容。

跟 v0.1.x 一样的分发模式，**SKILL 内容升级到 v1.0 工作流**。

## 8. 跟 wiki-manage v0.1.x 的关系

| | v0.1.x | v1.0 |
|---|---|---|
| AI 端 | SKILL（init/curate/lint 三个）| SKILL（升级，含「处理标记」工作流） |
| 知识协议 | 扁平 `me/projects/concepts/sources` | Karpathy `domains/global/staging/routes` |
| 团队仓 | 无 | **明确砍**（只服务个人） |
| Web 治理 | 无 | **有**（极简 MVP） |
| 用户标记 | 无 | **有**（v1.0 只支持「有疑问」） |
| 跨平台 | 三平台 plugin manifest | 同（Claude/Codex plugin + Cursor snippet） |
| Enforcement | 无 | **无**（明确不要 git hook） |

**实质增量**：Karpathy 协议 + Web 治理面板 + 用户标记驱动的 AI 整理工作流。
